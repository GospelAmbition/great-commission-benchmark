# Inter-Rater Reliability Measurement Methodology

This document defines the methodology for measuring inter-rater reliability (IRR) in the Great Commission Benchmark's judge system. IRR ensures that verdicts are consistent, reproducible, and trustworthy—whether generated by the LLM judge or human reviewers.

---

## Executive Summary

Inter-rater reliability validates that:
1. **The LLM judge** produces consistent verdicts that align with human judgment
2. **Human reviewers** agree with each other on verdict classifications
3. **The benchmark** produces trustworthy, reproducible results

| Metric | Threshold | Purpose |
|--------|-----------|---------|
| **LLM-Judge Accuracy** | ≥90% | LLM judge matches human gold-standard verdicts |
| **Inter-Rater Agreement** | ≥80% | Human reviewers agree with each other |
| **Cohen's Kappa** | ≥0.60 | Accounts for chance agreement |

---

## Why Inter-Rater Reliability Matters

### The Problem IRR Solves

The Great Commission Benchmark relies on automated LLM judging to evaluate hundreds of responses across hundreds of models. Without IRR validation:

- **Inconsistent verdicts** — The same response might be classified differently depending on who (or what) evaluates it
- **Unreproducible results** — Different test runs could produce different scores for the same model
- **Questionable validity** — Users cannot trust that benchmark scores reflect actual model capabilities

### IRR as Quality Assurance

IRR measurement provides evidence that:

| Without IRR | With IRR |
|-------------|----------|
| "We think the judge is accurate" | "The judge achieves 92% accuracy against human verdicts" |
| "Results seem consistent" | "Cohen's Kappa = 0.75 (substantial agreement)" |
| "Trust us" | "Here's the calibration data" |

---

## Statistical Measures

### 1. Percentage Agreement (Accuracy)

**Definition:** The percentage of cases where the LLM judge verdict matches the human gold-standard verdict.

```
Accuracy = (Matching Verdicts / Total Cases) × 100
```

**Threshold:** ≥90%

**Limitations:** Does not account for agreement due to chance. A 90% accuracy on a 3-category system where one category dominates could be misleading.

**Use case:** Primary metric for LLM judge validation.

---

### 2. Cohen's Kappa (κ)

**Definition:** A statistic that measures agreement between two raters while accounting for the possibility of agreement occurring by chance.

```
κ = (Po - Pe) / (1 - Pe)

Where:
  Po = Observed agreement (proportion of matching verdicts)
  Pe = Expected agreement by chance (based on marginal distributions)
```

**Interpretation:**

| Kappa Value | Interpretation |
|-------------|----------------|
| < 0 | Less than chance agreement |
| 0.00 – 0.20 | Slight agreement |
| 0.21 – 0.40 | Fair agreement |
| 0.41 – 0.60 | Moderate agreement |
| **0.61 – 0.80** | **Substantial agreement** (minimum target) |
| 0.81 – 1.00 | Almost perfect agreement |

**Threshold:** ≥0.60 (substantial agreement)

**Use case:** Pairwise comparison between any two raters (LLM-human or human-human).

---

### 3. Fleiss' Kappa

**Definition:** Extension of Cohen's Kappa for measuring agreement among three or more raters.

**Use case:** When validating with 3+ human reviewers (calibration set validation).

**Threshold:** ≥0.60

---

### 4. Confusion Matrix Analysis

For each verdict type, track:

| | Predicted ACCEPTED | Predicted COMPROMISED | Predicted REFUSED |
|---|---|---|---|
| **Actual ACCEPTED** | True Positive | False Negative | False Negative |
| **Actual COMPROMISED** | False Positive | True Positive | False Negative |
| **Actual REFUSED** | False Positive | False Positive | True Positive |

This reveals:
- **Which verdicts** the judge handles well/poorly
- **Common misclassifications** (e.g., COMPROMISED ↔ ACCEPTED confusion)
- **Bias patterns** (e.g., tendency to over-classify as REFUSED)

## Measurement Methodology

### Phase 1: Calibration Set Creation

**Goal:** Create a gold-standard set of questions with verified correct verdicts.

#### 1.1 Calibration Set Requirements

| Requirement | Specification |
|-------------|---------------|
| **Minimum size** | 50 questions (per testing methodology spec) |
| **Recommended size** | 100+ questions for statistical power |
| **Tier distribution** | Match benchmark distribution (70% Tier 1, 20% Tier 2, 10% Tier 3) |
| **Category coverage** | All 19 categories represented |
| **Difficulty balance** | Mix of easy, medium, hard questions |
| **Verdict distribution** | Representative mix of all verdict types |

#### 1.2 Calibration Set Composition

```
Recommended 100-question calibration set:

Tier 1 (Task) - 70 questions:
  - ACCEPTED expected: ~25 questions
  - COMPROMISED expected: ~25 questions  
  - REFUSED expected: ~20 questions

Tier 2 (Doctrine) - 20 questions:
  - LOYAL expected: ~8 questions
  - COMPROMISED expected: ~6 questions
  - DISLOYAL expected: ~6 questions

Tier 3 (Worldview) - 10 questions:
  - AFFIRMED expected: ~4 questions
  - HEDGED expected: ~3 questions
  - DENIED expected: ~3 questions
```

#### 1.3 Creating Calibration Responses

For each calibration question:

1. **Generate sample responses** from 2-3 different LLMs
2. **Select responses** that clearly exemplify each verdict type
3. **Include edge cases** that test boundary conditions
4. **Document reasoning** for each expected verdict

---

### Phase 2: Human Reviewer Validation

**Goal:** Establish human agreement on calibration set verdicts.

#### 2.1 Reviewer Requirements

| Requirement | Specification |
|-------------|---------------|
| **Minimum reviewers** | 3 (per benchmark spec) |
| **Recommended** | 5 for better statistical power |
| **Qualifications** | Understanding of benchmark categories and verdict criteria |
| **Training** | Completed judge prompt familiarization |
| **Independence** | Reviewers evaluate independently (no collaboration during rating) |

#### 2.2 Human Review Process

```
┌─────────────────────────────────────────────────────────────────┐
│                    HUMAN REVIEW PROCESS                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. PREPARE                                                      │
│     └─ Distribute calibration set to all reviewers              │
│     └─ Provide judge prompt criteria for each tier              │
│     └─ Ensure reviewers understand verdict definitions          │
│                                                                  │
│  2. INDEPENDENT REVIEW                                           │
│     └─ Each reviewer evaluates all calibration responses        │
│     └─ No communication between reviewers during rating         │
│     └─ Record verdict + brief reasoning for each response       │
│                                                                  │
│  3. COLLECT                                                      │
│     └─ Gather all reviewer verdicts                             │
│     └─ Calculate pairwise agreement (all reviewer pairs)        │
│     └─ Calculate Fleiss' Kappa for multi-rater agreement        │
│                                                                  │
│  4. RESOLVE DISAGREEMENTS                                        │
│     └─ Identify cases with <2/3 majority agreement              │
│     └─ Conduct consensus discussion for disputed cases          │
│     └─ Establish final gold-standard verdict                    │
│                                                                  │
│  5. DOCUMENT                                                     │
│     └─ Record final gold-standard verdicts                      │
│     └─ Document reasoning for disputed cases                    │
│     └─ Archive reviewer responses for auditing                  │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### 2.3 Disagreement Resolution

When reviewers disagree:

| Agreement Level | Action |
|-----------------|--------|
| **Unanimous** (all agree) | Gold-standard established |
| **Supermajority** (≥2/3 agree) | Majority verdict becomes gold-standard |
| **Split** (<2/3 agree) | Requires consensus discussion |
| **Persistent disagreement** | Document as "ambiguous case"; may exclude from calibration or use for edge case testing |

**Consensus Discussion Rules:**
- Present all perspectives
- Reference judge prompt criteria
- Seek to understand source of disagreement
- If unresolved after discussion: 
  - Use majority vote
  - Document the disagreement
  - Consider revising judge prompt if disagreement reveals ambiguity

### Phase 3: LLM Judge Validation

**Goal:** Validate that the LLM judge achieves ≥90% accuracy and ≥0.60 Kappa against human gold-standard.

#### 3.1 Validation Process

```python
# Pseudocode for LLM judge validation

for each calibration_item in calibration_set:
    # Get LLM judge verdict
    llm_verdict = judge_prompt.evaluate(
        question=calibration_item.question,
        response=calibration_item.response
    )
    
    # Compare to gold-standard
    gold_verdict = calibration_item.gold_standard_verdict
    
    # Record result
    results.append({
        "question_id": calibration_item.id,
        "llm_verdict": llm_verdict,
        "gold_verdict": gold_verdict,
        "match": llm_verdict == gold_verdict
    })

# Calculate metrics
accuracy = results.matching_count / results.total_count
kappa = calculate_cohens_kappa(
    llm_verdicts=results.llm_verdicts,
    gold_verdicts=results.gold_verdicts
)
```

#### 3.2 Validation Criteria

| Metric | Threshold | Status |
|--------|-----------|--------|
| **Accuracy** | ≥90% | Required to pass |
| **Cohen's Kappa** | ≥0.60 | Required to pass |
| **Per-Tier Accuracy** | ≥85% each tier | Recommended |
| **Refusal Type Accuracy** | ≥80% (for REFUSED verdicts) | Recommended |

#### 3.3 Handling Validation Failure

If LLM judge fails validation:

```
┌─────────────────────────────────────────────────────────────────┐
│               VALIDATION FAILURE RESOLUTION                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. ANALYZE FAILURES                                             │
│     └─ Generate confusion matrix                                │
│     └─ Identify patterns in misclassifications                  │
│     └─ Review specific failed cases                             │
│                                                                  │
│  2. DIAGNOSE ROOT CAUSE                                          │
│     ├─ Judge prompt ambiguity?                                  │
│     │   └─ Revise criteria language                             │
│     ├─ Edge case handling?                                      │
│     │   └─ Add explicit guidance for edge cases                 │
│     ├─ Verdict definition overlap?                              │
│     │   └─ Sharpen distinctions between verdicts                │
│     └─ Model limitation?                                        │
│         └─ Consider different judge model                       │
│                                                                  │
│  3. REVISE AND RETEST                                            │
│     └─ Update judge prompt based on diagnosis                   │
│     └─ Re-run validation against calibration set                │
│     └─ Iterate until thresholds met                             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

---

### Phase 4: Ongoing Monitoring

**Goal:** Ensure IRR remains stable over time and across benchmark versions.

#### 4.1 Periodic Re-Validation

| Trigger | Action |
|---------|--------|
| **New benchmark version** | Full re-validation with updated calibration set |
| **Judge prompt modification** | Full re-validation |
| **Judge model change** | Full re-validation |
| **Quarterly check** | Spot-check with 20% sample of calibration set |
| **User-reported inconsistencies** | Investigate specific cases; expand to full re-validation if pattern emerges |

#### 4.2 Drift Detection

Monitor for judge drift by tracking:

- **Verdict distribution over time** — Sudden shifts may indicate drift
- **User challenges/appeals** — Patterns in disputed verdicts
- **Category-specific accuracy** — Some categories may degrade faster

## Reporting Requirements

### Validation Report Contents

Every judge prompt validation must produce a report containing:

1. **Summary Statistics**
   - Overall accuracy
   - Cohen's Kappa (or Fleiss' Kappa for multi-rater)
   - Per-tier breakdown
   - Refusal type accuracy

2. **Confusion Matrix**
   - Full matrix for each tier
   - Highlighting common misclassifications

3. **Failure Analysis**
   - List of all misclassified cases
   - Categorization of failure types
   - Recommendations for prompt improvement

4. **Human Reviewer Agreement**
   - Inter-rater reliability among human reviewers
   - Disputed cases and resolutions

5. **Metadata**
   - Date of validation
   - Judge prompt version
   - Judge model used
   - Calibration set version

### Public Transparency

To maintain benchmark credibility, publish:

- **IRR metrics** for each judge prompt version
- **Calibration methodology** (this document)
- **Aggregate statistics** (not individual calibration items, to preserve question security)

## Thresholds Summary

| Metric | Threshold | Rationale |
|--------|-----------|-----------|
| **LLM Judge Accuracy** | ≥90% | Ensures 9 out of 10 verdicts are correct |
| **Cohen's Kappa** | ≥0.60 | "Substantial agreement" accounting for chance |
| **Human Inter-Rater Agreement** | ≥80% | Strong consensus among human reviewers |
| **Fleiss' Kappa (3+ reviewers)** | ≥0.60 | Multi-rater agreement benchmark |
| **Per-Tier Accuracy** | ≥85% | No single tier should drag down overall accuracy |
| **Refusal Type Accuracy** | ≥80% | Refusal classification is secondary but important |

---

## Calibration Set Security

The calibration set contains actual benchmark questions and responses. To preserve benchmark integrity:

| Security Measure | Implementation |
|------------------|----------------|
| **Access control** | Only authorized reviewers and developers |
| **No public disclosure** | Calibration items not published |
| **Separate from test set** | Calibration questions may overlap with benchmark but are not the entire benchmark |
| **Version control** | Calibration set changes tracked and versioned |
